三、P0 — 正确性与功能缺陷（10 项）

P0-1状态深层修改不触发 UI 刷新，多游戏依赖「隐式兜底」已修复
位置
SudokuPage.setNumber / KlotskiPage.moveBlock / SlidePuzzlePage.tapCell / MemoryCardPage.flipCard
现象
@Local 对数组只建立一层代理。this.board[r][c] = n（二维数组内层）、block.x = nx（数组内对象字段）、cards[idx].flipped = true 都不会被观测到。数独填入数字后界面完全无反应；其余三处之所以「看着正常」，只是因为同一函数里恰好有 stepCount++、flippedIdxs = [...] 等顶层赋值顺带触发了重渲染——属于脆弱的隐式依赖，任何一次重构都会让它静默失效。
建议
① 用 @ObservedV2 + @Trace 装饰数据类（Cell/Block/Card），让深层字段可观测；② 或统一「重建数组」模式并封装工具方法，杜绝原地改： 
// 推荐：不可变更新，@Local 一定能观测到
private updateCell(r: number, c: number, v: number): void {
  const next = this.board.map((row: number[], i: number) =>
    i === r ? row.map((x: number, j: number) => j === c ? v : x) : row);
  this.board = next;
}
P0-2数独生成器在主线程做逐格扫描回溯，困难档长尾卡顿已修复
位置
SudokuPage.generatePuzzle() / countSolutions() / solveCount()
现象
generatePuzzle() 在 aboutToAppear 中同步调用。困难难度需挖掉 58 个格子，每挖一格调一次 countSolutions()；而候选集计算走的是 canPlaceAt() 逐格扫描（每格 27 次读），MRV 选格又要对全部空格各算一遍候选，成本被放大约 20000 倍。
实测（桌面 Node，60 次采样）：困难档 p50 25ms、p99 111ms；普通档 p50 4.5ms、p99 20ms。按移动端相对桌面慢一个量级折算，困难档长尾约为 1.5 秒级的主线程冻结，期间 UI 不响应。
已实施
改用位掩码约束：行/列/宫各维护一个 9 位占用掩码，候选集由三次按位或 + 取反一次得到（~(row|col|box) & 0x1FF），MRV 选格用查表的 popcount。配 boxOf（下标→宫）与 bitToVal 两张查找表。
实测提速：困难档 20×（p99 111ms → 5.5ms，折算真机约 1.5s → 82ms）、普通档 15.6×、简单档 8.7×。已用独立朴素求解器对 120 个题面做交叉校验：唯一解、题面合法性、完整解合法性全部通过。
提速后长尾已降到百毫秒内，无需引入 taskpool／Worker，架构复杂度不变。
可选后续
① 缓存题面池，冷启动直接取用；② 若仍嫌慢，把生成移入 taskpool 并显示 loading；③ 困难档线索数 23 → 26 可再降一个量级（当前挖洞算法常停在 23~26，实际已有余量）。
P0-3数独兜底题面的去重指纹记录错位已修复
位置
SudokuPage.generatePuzzle() 第 250-251 行
现象
this.previousKey = this.boardKey(last); return this.fallbackPuzzle(); — 记录的指纹来自变量 last，实际返回的却是 fallback 题面。指纹与实际题面不一致，去重机制失效，下次仍可能重复生成同一 fallback。
建议
改为对真正返回的对象取指纹：const fb = this.fallbackPuzzle(); this.previousKey = this.boardKey(fb); return fb;。另外三个 fallback 题面未经唯一解校验，困难档 23 线索题面可能存在多解，建议校验后固化。
P0-4LightColors 与 DarkColors 内容完全重复，90 行冗余 + 语义倒挂已修复
位置
DesignTokens.ets 第 38-128 行
现象
两个类的 40 个字段逐一引用同一批 $r('app.color.*') 资源，取值完全相同。主题适配实际由资源目录（base/ 与 dark/）完成，这两个类只是同一批资源的两个别名。后果：① 新增一个语义色要改两处；② 语义严重倒挂——Index.ets 的亮色页面写着 DarkColors.surfaceTranslucent，游戏页又混用 LightColors，代码读起来完全无法判断当前处于哪套主题。
建议
合并为单一 SemanticColors（语义令牌本就不分明暗，明暗由资源决定）： 
export class SemanticColors {
  static bg: Resource = $r('app.color.bg');
  static surface: Resource = $r('app.color.surface');
  // …其余 38 项
}
全局替换引用（约 300 处，可脚本化），删除 DarkColors。若确实需要「强制深色」场景（如启动闪屏），单独建 BrandColors 常量类即可，当前已存在。
P0-540+ 处硬编码颜色，深色模式下多处对比度失效已修复
位置
Game2048Page.getCellBg/getTileFontColor（14 处）、TetrisGamePage.SHAPE_COLORS（7 处）、MinesweeperPage.getNumColor（9 处）、KlotskiPage.getBlockBg（4 处）、Index.SplashLayer（6 处）等
现象
违反项目 AGENTS.md 中「UI 引用的常量应定义为 resources 资源值并用 $r(...) 引用」。最严重的是 2048：2/4 用浅米色底 #EEE4DA 配深字 #776E65，8 以上用亮色底配 #FFFFFF——这套配色只在亮色下成立，切到深色模式后浅底格子与深色棋盘割裂，且白色数字在 #F2B179 等浅橙底上几乎不可读。SplashLayer 的深色渐变（#16205F/#2A2B7E）则反过来在亮色下没有适配。
建议
① 把 2048 色板、俄罗斯方块色板、扫雷数字色、棋子色全部抽到 color.json，并在 dark/ 下提供对应值；② 至少做到「文字色跟随主题」——浅底配深字、深底配浅字，可用一个 getOnColor(bg) 亮度判断函数兜底；③ SplashLayer 固定深色是合理的（品牌页），但应显式注释说明这是刻意为之，避免后续被「修」掉。
P0-610 个游戏页全部未做安全区适配，底部控件被手势条遮挡已修复
位置
全项目 expandSafeArea 仅 Index.ets 第 305 行 1 处
现象
除首页外，所有游戏页的根容器都没有安全区处理。在全面屏（手势导航）设备上，俄罗斯方块的「加速下落」按钮、贪吃蛇与华容道的 ControlPad 方向键、猜数字的九宫格键盘都会落在底部手势区内，导致误触或点不到。
建议
给每个游戏页根容器补：.expandSafeArea([SafeAreaType.SYSTEM], [SafeAreaEdge.BOTTOM, SafeAreaEdge.TOP])；或更稳妥的是给底部操作区加动态 padding（通过 window.getWindowAvoidArea() 取避让区高度）。建议前者，改动最小。
订正
原建议方向有误，实施时已改用动态 padding。核查后发现：expandSafeArea 的语义是让组件突破安全区向外延伸，而本应用未开启全屏（EntryAbility 未调 setWindowLayoutFullScreen），页面本就位于安全区内——此时再加 expandSafeArea 反而会把内容顶到手势条下面。另外 Index.ets 第 305 行那处 expandSafeArea 挂在 Navigation 内部的首页容器上，只影响首页 Tabs，与游戏页无关。
实际方案
① 新增 common/SafeAreaInsets.ets，在 EntryAbility.onWindowStageCreate 中通过 getWindowAvoidArea(AvoidAreaType.TYPE_NAVIGATION_INDICATOR) 取底部避让高度，px 转 vp 后存入静态字段，并监听 avoidAreaChange 实时更新；② 10 个游戏页在内容层 Column（非背景层，背景仍铺满）追加 .padding({ bottom: this.safeBottom })，页面持 @Local safeBottom。该值在手势导航下为手势条高度、三键导航下为 0，不会与系统避让重复计算；读取失败时退化为 0，无副作用。
P0-7切后台时游戏不暂停，计时器持续运行已修复
位置
SnakeGamePage / TetrisGamePage / WhackMolePage / MinesweeperPage
现象
isPaused 仅在用户手动点击暂停时被设置。应用切到后台（onPageHide）时没有任何处理，setInterval 仍在跑：贪吃蛇会一直撞墙直到 game over，打地鼠 30 秒直接耗尽，扫雷计时器虚增。用户切回来的第一眼是「游戏结束」。
建议
在各游戏页补充生命周期钩子：onPageHide() 中记录并置 isPaused = true、clearInterval；onPageShow() 中恢复。可抽一个 GameLifecycleMixin 或在 GameHeader 层面统一处理，避免 10 处重复。
P0-8GamePanel 是死代码，且内部混用了与 Navigation 冲突的 router API已修复
位置
components/GamePanel.ets（69 行，全项目零引用）
现象
组件从未被任何页面使用，却在第 43 行写了 this.getUIContext().getRouter().back()。项目路由体系是 NavPathStack，router 是另一套独立栈——一旦有人图省事引用了这个「现成组件」，返回按钮会静默失效（router 栈为空，pop 无效果）。这是一颗埋好的雷。
建议
直接删除。若想保留这个「标准化外框」抽象，先改造成 @Param pathStack: NavPathStack + pathStack.pop()，并把 10 个游戏页统一迁移过去（可一并解决 P1-3 的结构重复）。
P0-9持久化重复全量写入，flush 未防抖已修复
位置
GameDataManager.persist() / updateHighScore() / incrementPlayCount()
现象
startGame() 里常连续调用 updateHighScore() 和 incrementPlayCount()，两者各自触发一次 persist()：每次都全量遍历 10 个游戏 → 构造两个 Record → 两次 JSON.stringify → 两次 putSync → 一次 flush。等于一次开局做了 2 遍完整序列化 + 2 次磁盘 IO。且 flush() 返回 Promise 却未 await、也未做防抖，高频操作下存在写入丢失风险。
建议
① 抽出 markDirty()，合并同帧内的多次变更，用 200ms 防抖统一落盘；② flush() 改为 await store.flush() 或至少挂 .catch() 记录错误；③ 所有空 catch 补上 hilog.error——当前初始化失败会让 store = null，之后所有最高分静默丢失，用户与开发者都无从察觉。
P0-10猜数字是唯一未接入数据层的游戏已修复
位置
pages/puzzle/GuessNumberPage.ets（全文无 GameDataManager 引用）
现象
其余 9 款游戏都记录最高分与游玩次数，只有猜数字不记录。首页「最高分排行」里它永远显示 --，且该玩法的天然指标是「最少猜测次数」，比分数更有意义，目前完全没有沉淀。
建议
在 submit() 胜利分支补 GameDataManager.updateHighScore('guessnumber', 分数)，分数可设计为 基础分 × 难度系数 − 尝试次数。同时建议给 GameInfo 增加一个 scoreLabel 字段（「分」/「步」/「次」/「秒」），让首页排行对每款游戏显示正确单位——当前排行把华容道的「步数换算分」和贪吃蛇的「得分」混在一起排序，语义上其实是错位的。

每个页面都写一遍：display.getDefaultDisplaySync() → px2vp(d.width) → Math.max(min, Math.floor((Math.min(wVp, max) - pad) / N))，只有魔数不同。更关键的是 getDefaultDisplaySync() 取的是整个屏幕的物理宽度，不是页面可用宽度——在分屏、自由窗口、折叠屏展开态下算出的格子尺寸会偏大，棋盘溢出屏幕。
建议
① 抽 common/ScreenUtils.ets：calcCell(count, maxWidth, padding, minSize)；② 宽度来源改为 this.getUIContext().getWindowWidth()（跟随窗口）或在棋盘容器上加 .onAreaChange() 取实际布局宽度——后者最准确，也天然支持旋转与分屏。
实际处理
新增 common/ScreenUtils.ets（calcCell(count, maxWidth, padding, minSize)），8 处重复实现收敛为一行调用（各自魔数保留）。原建议的 getUIContext().getWindowWidth() 在 SDK 类型定义中不存在（grep 全 SDK 的 .d.ts 无此 API，照写会编译失败）——已改用 window.getWindowProperties().windowRect.width（px，官方 FAQ 同款写法），由 EntryAbility 初始化并监听 windowSizeChange（分屏/自由窗口/折叠屏/旋转都会触发）保持最新；未初始化时回退到屏幕宽度，不劣化。顺带：原先 6 条 getDefaultDisplaySync 固有告警随之消失。

P1-6游戏逻辑与 UI 强耦合，无法单测、无法复用

P1-7GameStatus 枚举已定义但从未使用，状态由三个布尔拼出已修复

五、P2 — 性能与体验（11 项）

P2-1全项目 0 处 renderGroup，违反工程自身规范
位置
全项目（grep renderGroup 零命中）
现象
AGENTS.md 第三节明确要求「含复杂子组件的动画，将其设为 renderGroup(true)，减少渲染批次」，但全项目一处都没用。2048 的缩放动画、数独的双指缩放、启动闪屏的渐显，都涉及大量子节点的合成，缺少离屏缓存会明显掉帧。
建议
给以下容器补 .renderGroup(true)：2048 的棋盘容器、数独的缩放棋盘、SplashLayer 的图标块、以及各游戏的结算弹窗卡片。
P2-2贪吃蛇每 tick 的渲染是 O(n²)，满屏时约 16 万次比较
位置
SnakeGamePage.getCellColor() / isSnakeCell()
现象
渲染 400 个格子，每格调一次 isSnakeCell()，后者线性遍历整个蛇身。蛇长接近 400 时，单帧需要 400 × 400 = 约 16 万次坐标比较，每 180ms 执行一次（困难难度 120ms）。中低端机上会明显卡顿。
建议
维护一张 occupied: boolean[][]（或 Set<number>，key 用 r * COLS + c）占用表，随蛇移动增量更新，查询降为 O(1)。单帧比较次数从 16 万降到 400。
P2-3棋盘用 ForEach 全量重建，未使用复用或 Canvas
位置
Snake(400) / Tetris(200) / Sudoku(81) / Minesweeper(81) / 2048(16) / 华容道(20) 等
现象
每个格子是一个 Column 节点，棋盘状态一变就触发全量 diff。贪吃蛇 400 个节点每 180ms 全量重建一次；俄罗斯方块每下落一格重建 200 个节点，且 drop() 每次都 commitBlock() 新建对象（60fps 下 GC 压力显著）。
建议
① 格子抽成 @Reusable 组件并配合稳定的 key，让 ArkUI 复用节点；② 对高频重绘的贪吃蛇/俄罗斯方块，改用 Canvas + CanvasRenderingContext2D 直接绘制，把 400 个节点压成 1 个；③ 俄罗斯方块的 commitBlock() 改为只更新 x/y 两个 @Trace 字段，不再整体重建对象。
P2-42048 的动画机制混乱，位移从未实现
位置
Game2048Page.syncTilesFromBoard() / animateMergedTile() / animateNewTile() / getTileAnimation()
现象
三处问题叠加：① TileData 里的 offsetX/offsetY 从未被赋过非零值——没有实现格子从旧位置滑到新位置的位移动画，所谓「带滑动动画」实际只有原地缩放；② 同时混用 .animation() 属性动画与 animateTo() 命令式动画，两套机制会互相打断；③ animateMergedTile / animateNewTile 内部有 3 层嵌套 animateTo + onFinish 回调链，isNew 标志被反复翻转，是 ArkUI 明确不推荐的写法。
建议
统一到一种机制（推荐保留 .animation() 属性动画，配合状态驱动）。为 Tile 增加 fromRow/fromCol 与 toRow/toCol，在一次状态变更中同时设置 offset（起始位移）与目标位置（0），让系统自动插值出滑动效果。删除所有嵌套 animateTo。
P2-5启动闪屏 2.3 秒且不可跳过
位置
Index.startSplash() 第 132-160 行
现象
三层嵌套 setTimeout，总时长 600+600+300+800 ≈ 2300ms。期间主页内容已在下层完成渲染但被完全遮挡，用户只能干等，且没有任何跳过入口。对一个小游戏合集而言，这个启动成本过高。
建议
① 总时长压到 1000~1200ms；② 用单个 animateTo + delay 或 curve 编排替代嵌套 setTimeout，可读性更好也更易调整；③ 闪屏层加「点击跳过」；④ 考虑用 startWindowIcon 承接首帧，把闪屏做成纯内容淡出而非独立等待期。
P2-6冷启动重复加载数据两次，Collator 反复构造
位置
Index.aboutToAppear() 第 60-61 行 与 onPageShow() 第 75-77 行
现象
两个生命周期都调用 loadData()，冷启动时执行两遍完整加载（5 次 GameDataManager 查询 + 一次拼音排序）。而 sortByPinyin() 每次都 new intl.Collator('zh-CN', {collation:'pinyin'})——Collator 构造是重操作，每次进出游戏页返回首页都要重建一遍。

P2-7isTablet 是死状态，却会触发全局重渲染
位置

@Local isTablet 注册了媒体查询监听，每次断点跨越都会改变并触发整个 Index 重渲染，但 build() 里从未读取过它——响应式布局实际由 GridRow 的 breakpoints 独立完成。纯粹的无谓开销。

Index.loadData() 第 80 行 与 第 84 行
现象
featuredGames 与 rankedGames 都取自 GameDataManager.getTopGames(6)，内容一模一样，却各做了一次「复制 10 项 + 排序 + 切片」。命名上「精选」与「排行」也确实指向同一份数据，语义冗余。

P2-92048 用 JSON.stringify 比较棋盘是否变化

现象
每次滑动做两次 JSON.stringify(4×4 数组) 再比较字符串，用于判断「本次滑动是否有效」。虽然 16 个数字的量级下开销不大，但这是用序列化做相等性判断，既低效也不易读。

P2-10扫雷连锁展开的 BFS 使用 Array.shift()
位置
MinesweeperPage.reveal() 第 136-151 行
现象
const p = q.shift()! — Array.shift() 会移动后续所有元素，是 O(n) 操作。81 格的棋盘影响有限，但在困难难度大面积连锁展开时仍是无谓开销，且写法不如索引指针清晰。
建议
改用头指针：let head = 0; while (head < q.length) { const p = q[head++]; … }，把 BFS 降为严格 O(n)。另外 q 存的是 [r, c] 数组，可改为存单个整数 r * COLS + c，减少对象分配。
